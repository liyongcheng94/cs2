# CS2HQ 数据口径审计报告

> 2026-11-26 · Phase 1（七项需求之①）· 工具：`.e2e/audit30.py`（容器内只读扫描 60 条 DemoAnalysis / 96 条 MatchStat / 92 场 Match）

## 审计范围与方法
- 全量扫描 `demoanalysis.payload` 嵌套字段（NaN / 数值越界 / 字段在场率）
- `match.win` 与 `score1/score2` 交叉验证
- `matchstat` 数值列健全性
- 比分/胜负的消费方代码排查（backend/app + frontend/src 全量 grep）

## 结论

### ① 比分口径：score1=我方, score2=敌方（此前记录反了，已纠正）
- 写入逻辑 `backend/app/services/wanmei_sync.py:46-51`：`win = winTeam == team`（权威），score1/score2 为 API 原始顺序。实测 92 场交叉验证：**score1 为我方得分**（如 `PVP@9210603844271111948` win=True, score1=13, score2=5）。
- 此前会话记录「score1/score2 是（敌方,我方）」**是错的**；正确记忆：「临时脚本用 score1>score2 判胜负错在没用 match.win，而非顺序本身」——任何胜负判断必须用 `match.win`（winTeam==team 推导），比分只作展示。
- 消费方排查：无应用代码按反口径消费；前端 `App.tsx:131` / `MatchDetailModal.tsx:130` 直接展示 `score1 : score2`（我方在前，符合习惯），无需改代码。

### ② `match.win` 列健康
- winTeam/team 字段齐全的场次 win 全部与比分自洽；兜底分支（winTeam 缺失时按 my_team=1 推导）仅在老数据可能触发，本次扫描未见异常。

### ③ DemoAnalysis payload 字段在场率（schema 演进痕迹，聚合时必须容错）
| 字段 | 在场 / 总数 | 说明 |
|---|---|---|
| meta / match_id / schema_version | 60/60 | 稳定 |
| pistol_rounds | 30/30 | 手枪局 v2 后全量回填 |
| utility | 27/60 | 33 条为旧 schema（utility 入库前），聚合基线画像时须跳过 None |
| server_ratings（顶层） | 0/60 | 实际挂在 `utility.server_ratings` 下，顶层键恒 None——**顶层读取必得 None，别误判为数据丢失** |
- 无 NaN、无越界数值（rating/kast/adpr/kills 等 SUSPECT_RANGES 全过）。

### ④ MatchStat 列
- `hs_rate/adr/rws/we/kills...` 结构正常；审计脚本早期引用的 `kast/head_shot_rate/entry_kill/entry_death` **列不存在**（已确认 models.py 无这些列，无死列消费）。
- `detail_json`（v1 全场详细数据缓存）是逐场十人数据的权威缓存。

### ⑤ 遗留口径名问题：已闭环
- report prompt 已含「口径注意：utility.waste_rate 是闪光效率浪费（扔了没致盲人≥0.5s），不要与道具买而不扔（usage[].waste_rate）混用」（`report.py:62`）。
- 新增守护测试 `tests/test_report.py::test_ai_review_prompt_carries_waste_rate_glossary`（9 passed）。

## 对后续 Phase 的约束
1. **基线画像 / 定位分析聚合**：遇 `payload["utility"] is None` 跳过该场并在响应中注明样本数；server_ratings 一律从 `utility.server_ratings.players` 读。
2. **胜负口径**：所有统计、报告、新页面一律 `match.win`；比分仅展示（我方:敌方）。
3. **位置表（Phase 3）**：deaths 坐标字段（victim_x/y、killer_x/y）在场率 100%，可作为分区统计底座。
4. 历史旧 schema 场次（utility=None）如需参与聚合，仅用其可用维度，不得补零拉均值。

## 已知不可采信数据（沿用既有结论）
- 完美平台接口 `entryDeath` 恒 0 → 不用；首死统计走 demo deaths 推导。
- `kast` 接口口径异常 → 不展示。
